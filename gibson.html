A tour of GIBSON's 3270 front end

Status: DRAFT. Staged here as a candidate contribution to the GIBSON project — not yet submitted upstream. If you're reading this anywhere other than a Panelwright working tree, it's probably already been adopted or superseded; check the GIBSON repo for the current version.

GIBSON is an independent, Python-based educational mainframe simulator — no IBM affiliation, no IBM code — built to give security learners a safe place to practise TSO, ISPF, RACF, JES, CICS, Db2, OMVS and more against a system that behaves the way a real z/OS installation does. It's the platform behind the Hacking Mainframes course material, and it ships with two CICS banking applications (a "normal" one and a deliberately vulnerable one) so security exercises land against data that means something.

This tour is about one specific claim GIBSON makes about itself: that its native front end on port 23 is a real TN3270/3270-datastream implementation, not a text approximation of one. That claim matters, because it's the difference between "a green-screen-themed web app" and "something a real 3270 client — c3270, x3270, or any automation built on the actual protocol — can drive." We checked, and it holds up:

  • A raw socket connect to GIBSON's TN3270 port receives real Telnet IAC negotiation bytes unprompted: IAC DO TN3270E, IAC WILL/DO BINARY, IAC WILL/DO EOR, IAC DO TERMINAL-TYPE. That's genuine TN3270E, not a banner.
  • Its outbound datastream uses real 3270 primitives — Erase/Write, SBA (Set Buffer Address) with correctly 6-bit-encoded buffer addresses, SFE (Start Field Extended) with real IBM extended-attribute type codes for colour and highlighting, text in real CP037 EBCDIC, and correct IAC byte-doubling — not a lookalike.
  • It decodes correctly in s3270, the reference scriptable 3270 client: ReadBuffer(Ascii) dumps show real, distinct field attributes throughout — protected labels, unprotected input fields, and genuinely non-display password/token fields.

Every screenshot below is a real SFE/SBA/colour-attribute 3270 screen rendered by GIBSON and captured live, not a mockup.

Quick start

git clone https://github.com/kmilne40/GIBSON.git
cd GIBSON/gibson-mainframe
docker build -t gibson-mainframe .
docker run -d -p 3270:3270 -p 2023:2023 gibson-mainframe

Connect with any real 3270 client:

c3270 -model 3278-2-E localhost 3270      # or: telnet localhost 2023

Default credentials: IBMUSER/SYS1 (SPECIAL authority, and — as the source itself documents — GIBSON's designated break-glass account) and GUEST/GUEST (no authority). From the initial selector screen, log on with L TSO, L CICS, L DB2, L IMS, L ZVM, or L TPF depending on which subsystem you want to reach first.

As an aside: the screenshots in this document were captured using Panelwright — an open-source, pure-TypeScript 3270 automation library — driving GIBSON through its own CLI rather than a human at a keyboard. That's a reasonable way to batch-capture a tour like this one, but it's not the point of this document; any 3270 client works identically for a human.

Access and terminals

The VTAM-style selector

The very first screen is a VTAM-flavoured application selector — LU name, client IP/port, and sense code are all filled in live per connection, and one field lets you route to six different subsystems (L TSO, L CICS, L DB2, L IMS, L ZVM, L TPF) without reconnecting. This is a nice piece of realism: a real z/OS shop's VTAM network typically does have one front door like this in front of several application IDs.

TSO/E LOGON, with MFA and forced-password-change fields already present

The real TSO/E LOGON panel — note the New Password and MFA Token fields sit right there on the standard panel, not bolted on. We drove this tour as IBMUSER, which GIBSON's own source (core/security_mode.py, core/state.py) documents as an explicit, audited break-glass account exempt from the MFA check — so we didn't trigger the MFA/forced- password-change flow live in this pass (see "what this tour didn't cover" below). The mechanism is real and enforced server-side, though: state.py implements mfa_token()/validate_mfa_token() and logs a MFA_BREAKGLASS_USED event specifically for this exemption path — worth a follow-up tour with a non-break-glass user under the "secure" security profile.

A real TSO READY banner

Standard ICH70001I ... LAST ACCESS RACF banner, followed by a system message pointing at HELP, ISPF, and SDSF — a nice bit of in-band onboarding for a first-time learner.

TSO, ISPF, SDSF, and batch

ISPF Primary Option Menu, with real extended-attribute colour

This is not a static-colour theme — it's genuine per-field SFE extended-attribute painting. Reading the field-level colour data straight off the wire (panelwright screen --json's styleRuns) for this exact screen shows real per-region colours: white for the title, blue for the action bar and background, green for the Option ===> prompt, turquoise for the input area. A wire trace of this exact panel is at traces/gibson-tour/04-ispf-primary-menu.json in this repo if you want to see the raw orders.

The menu itself reaches an unusually wide set of subsystems from one place — RACF admin (R), SDSF (S), DB2I/SPUFI (12), IMS Connect (I) — alongside the standard ISPF options.

Data Set List Utility (3.4)

The 3.4 fast-path jump works exactly like real ISPF, and IBMUSER comes pre-seeded with a small set of labelled learning datasets — IBMUSER.COBOL.LAB, IBMUSER.JCL.LAB, IBMUSER.REXX.LAB, IBMUSER.SQL.LAB — one PDS per language GIBSON's own interpreter stack supports.

Browsing a real REXX exec

Member-list, then Browse, on IBMUSER.REXX.LAB(HELLO) — real REXX source, runnable against GIBSON's own REXX interpreter (per the capabilities overview, roughly 2,200 lines of interpreter behind it).

SDSF

The standard SDSF primary menu (AD/DA/ST/I/O/H/INIT/...) — selecting ST (status of jobs) gives a seeded, varied job queue:

Six jobs across five different real JES2 states — OUTPUT, HELD, EXECUTIO[N], FAILED, ACTIVE — a good one-screen demonstration of the JES2 lifecycle for a learner who's never seen a spool before. Trace: traces/gibson-tour/10-sdsf-job-status.json.

Security administration

RACF Services Option Menu

Reached via ISPF option R. The panel itself tells you what's actually happening underneath: "Actions echo the equivalent RACF command and write SMF type-80." That's a real design commitment, not marketing copy — we verified it below.

A genuine LISTGRP result

Selecting group-profile administration, listing SYS1, produces a real LISTGRP SYS1 command echo and a real result: GROUP=SYS1 OWNER=IBMUSER SUPGROUP=SYS1, with connected users and their authority levels (IBMUSER AUTHORITY=JOIN, RUARIV AUTHORITY=USE). This is genuinely useful for a RACF-admin lab — the panel isn't a facade over a canned string, it ran a real command against GIBSON's live SYS1.RACFDS-style security database.

Applications and databases

CICS: a genuinely unformatted transaction-entry screen

L CICS from the selector lands you on a genuinely unformatted 3270 screen — zero fields, by design, exactly like a real CICS terminal waiting for a transaction ID. This is a good, honest touch: a lot of "3270-styled" simulators fake this with an invisible input field; GIBSON doesn't, and a 3270-aware client has to handle it as the unformatted case it really is (send the AID with the raw buffer, no field-relative typing). Typing CESN here and pressing Enter reaches the real sign-on panel:

DFHCE3549 Sign-on is complete — that message ID is the real CICS message GIBSON is reproducing.

CEMT — the master terminal transaction

CEMT I TASK gives a real inquire-task display, including CICS's own DFHSIP system-initialization task, with the standard overtype-to-modify convention (Act column) intact.

DVCA — the deliberately vulnerable banking app

DVCA ("Mel's Cargo — Office Supply Store") is GIBSON's intentionally vulnerable CICS application, the counterpart to the properly-secured CBSA. Note the footer: PA1/PA3 and transaction escape can be explored in vulnerable lab — this is the kind of screen a security-testing exercise targets, and it's worth exploring with an eye specifically for what a secure-profile run of the same panel looks like differently (we didn't do that comparison in this pass — see below).

CBSA — the "real" banking core, behind its own layered auth

Interesting detail: CBSA isn't just "the non-vulnerable DVCA" — it sits behind its own second authentication layer (CBPP/GACF pre-authentication), on top of the CICS-level CESN sign-on we already did. That's a believable shape for a real banking core system, and a good demonstration that "signed on to CICS" and "authorized into this specific banking application" are deliberately two different gates here. Trace: traces/gibson-tour/16-cics-cbsa-gacf.json.

IMS

L IMS from the selector gives a genuine /SIGN-driven IMS message region terminal — the classic DFS3650I/DFS3649A IMS message IDs, and the same /SIGN ON userid password-then-transaction-code interaction model real IMS terminals use.

z/VM

L ZVM reaches a full z/VM 7.4.0 LOGON screen (ZVMPROD at ZVMSYS1), complete with the standard IBM copyright banner and the LOGON-vs-DIAL distinction real z/VM presents.

Db2 / SPUFI

The DB2I primary option menu, reached via ISPF's own 12 fast-path. Running a real query through SPUFI (SELECT * FROM SYSIBM.SYSTABLES) returns a genuine catalog listing — and it's populated with a believable banking schema, not placeholder rows:

CUSTOMER, ACCOUNT, TRANSACTION, AUDITLOG, BATCH_TRANSFER, PAYMENT_BATCH — this is the same banking data model DVCA/CBSA operate against from the CICS side, which is exactly the kind of cross-subsystem coherence GIBSON's own docs describe as a design goal.

OMVS / USS

OMVS from TSO READY drops into a real Unix System Services shell — /u/ibmuser $, and id returns a believable uid/gid/groups triple for the logged-on user. Useful groundwork for anyone planning to run GIBSON's racf2john/John-the-Ripper credential-cracking lab from here.

What this tour didn't cover

This was a breadth-first pass, not an exhaustive one. Left for a future contributor, roughly in order of how quickly they'd be reachable from what's already documented above:

  • MFA and forced-password-change, live — we confirmed the mechanism is real and server-enforced (see the TSO logon section above) but didn't trigger it, because IBMUSER is GIBSON's designated break-glass account. Worth doing with a different user and/or the secure security profile (GIBSON_SECURITY_MODE=secure), which per the capabilities overview also flips on transport protection and RACLISTed sensitive classes — a genuinely interesting secure-vs-vulnerable side-by-side comparison for several of the CICS/RACF screens above.
  • Force-abend demonstrations and SYSUDUMP (S0C7/S806/S913/S0C4/S322/ Bx37) — the capabilities overview promises these; we didn't find the trigger command in a quick pass through HELP COMMANDS/HELP ABEND and the seeded IBMUSER.JCL.LAB members (PROCDEMO, SURRJOB, TSHOCK — none of which turned out to be the abend demo). Worth grepping the GIBSON source directly for whatever triggers this.
  • ACF2 — the alternative security manager. Presumably reachable via a differently-configured LPAR/profile rather than this same TSO session.
  • JCL submit → JES2 spool → SDSF output browse, end to end (we saw SDSF's job-status view with pre-seeded jobs, but didn't submit and watch one land ourselves).
  • RACF ADDUSER/PERMIT/SETROPTS as write operations (we only did a read via LISTGRP) — and the accompanying zSecure-style review / master-console alert / SMF record it should produce, per the cross-system-coherence claim.
  • NJE (the GIBSON/HAL/ORAC multi-node setup), zTPF, IND$FILE transfer, and the racf2john/John the Ripper OMVS lab.
  • CTF mode.

If you pick any of these up, the shape to follow is the same as above: get to a real, working state (not just the menu that leads there), grab one screen --format svg per interesting moment, and say in plain English what's actually being demonstrated.
