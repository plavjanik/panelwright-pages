Panelwright, the x3270 family, and the commercial emulators

Three different answers to "drive a 3270 application from a program". They overlap less than the shared protocol suggests: one is a terminal emulator suite with a scripting port, one is a desktop product with a decades-old automation API, and one is built for agents and for handing a live session back and forth with a human.

How to read this. The Panelwright column is drawn from this repository — its shipped commands, design records and live test evidence — and the same honesty rule applies here as in the project's host compatibility matrix: a cell states what has been built and exercised, never what should work. The other two columns are compiled from vendor and project documentation, cited at the foot of the page. Where a vendor's current capability could not be verified from public documentation, the cell says so rather than guessing — commercial emulators are large products and absence of a citation here is not absence of the feature. Corrections are welcome as an issue on the repository.

What each one is for

The honest starting point is that these tools were built for different jobs, and the matrix below is only meaningful once that is clear.

The reference implementation

The x3270 family

Paul Mattes' BSD-licensed suite: x3270 (X11), c3270 (curses), wc3270 (Windows console), s3270/ws3270 (script-only), b3270 (a protocol back end speaking XML or JSON to a front end of your choice), tcl3270 and the pr3287 printer. Thirty years old, in every Linux distribution, and the closest thing the 3270 world has to a specification you can execute.

The desktop products

Emulators with an automation API

IBM Personal Communications, Rocket and OpenText's Reflection and Host Explorer lines, BlueZone and their peers. Licensed desktop software whose automation story descends from HLLAPI — IBM's 1986 interface for reading the presentation space and sending keystrokes — through EHLLAPI and, for PCOMM, the Host Access Class Library for Java, C++, VB and VBScript, plus recorded macros.

This project

Panelwright

Pure TypeScript, modelled on Playwright rather than on expect: a daemon holds the session while a CLI, a terminal UI and a VS Code panel take turns driving it. Built first for an AI agent following a long procedure, and second for the person who has to watch that agent and take the keyboard when a screen needs judgement.

Driving a screen from a program

This is where the three diverge most. All of them can send keystrokes and read cells back; what differs is how you say which cell, and what happens while you wait.

Where Panelwright is the wrong choice

A comparison that only flatters its author is not worth publishing, and these are real.

  • You need a proven, supported desktop emulator for end users. That is exactly what the commercial products are, with support contracts, accessibility work, printer sessions and decades of deployment behind them. Panelwright is not a replacement for a trading floor's terminal estate.
  • You want the reference behaviour of the protocol. Use the x3270 family. This project treats s3270 and c3270 as its differential oracle: when Panelwright disagrees with them about a host, the working assumption is that Panelwright is wrong, and two real client defects were found and fixed exactly that way.
  • You have an existing HLLAPI estate. Decades of working EHLLAPI automation is not a thing to rewrite because a newer tool has nicer locators.
  • You need breadth of platform or protocol today. Panelwright is 3270 only, and its tested platform matrix is narrow. No 5250, no VT.
  • You need it to be maintained by someone other than a very small project. It is new, and it says so in its own compatibility matrix.
